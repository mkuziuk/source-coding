```
./run.sh 1.1 [--seed S] файл.json N                     # режим 1
./run.sh 1.1 --mode 2 [--seed S] файл.json N a1 ... ar  # режим 2
```

## 4. Расширение формата

Спецификация: FORMAT.md.

В разширение добавлены 3 поля: memory (глубина памяти d), initial (распределение первых d символов) и transitions (какая модель выбирает следующий символ после каждых d символов).

Чтобы получить неэргодичность для стационарного источника, нужен случайный выбор, который действует на все такты сразу. Поле mixture перечисляет компоненты с весами. В начале один раз выбирается источник, и дальше всю реализацию выдаёт только он.

# Задача 1.2. Равномерное кодирование источника без памяти

## Запуск

`./run.sh 1.2 файл.json` # режим 1

`./run.sh 1.2 --mode 2 [--nmax 50] [--code code.txt] файл.json R eps q`  # режим 2

## Тестовый источник

`memoryless.json`: k = 4, M = 3, L = 3. В нём 3 переключателя по разному смешивают модел и выдают одно распределение P = (1/2, 1/4, 1/8, 1/8). H(X) = 1.75 бит.
Параметры варианта: q = 5, eps = 10^-3.

## Проверка в режиме 1

Проверки для этого режим я осуществил следующим образом:
- если есть `memory` - у источника есть память;
- если смесь разных компонент - такты зависимы;
- в исходном формате (первая часть задачи 1) на всех позициях source распределение символа должно быть одинаковым.

## Типы блоков

Вероятность блока зависит только от того, сколько раз в нём встречается каждый символ.
Для каждого типа считаем вероятность одного блока и число блоков: n! / (c_1! ... c_k!).
Сортируем типы по убыванию вероятности и набираем q^l блоков.
P_e = 1 - вероятность набранных блоков.

Типов C(n+k-1, k-1): при n = 50, k = 4 их 23 426, при k = 5 получаем 316 251.
Для одного n: перебор типов и сортировка, O(T log T), где T - число типов.

Время работы при n_max = 50: около 8 с при k = 5 (лимит 10 с).

## Точность

Вероятности p_j = a_j / D приводятся к общему знаменателю. Вероятность блока равна
a_1^c_1 ... a_k^c_k / D^n. Знаменатель D^n у всех блоков общий, поэтому сортируем и складываем
только целые числители. А потом уже в конце создаётся Fraction.

Вот варианты, которые я попробовал, отбросил:
- Fraction на каждом шаге: точно, но 34 с при k = 5 (лимит 10 с);
- float и логарифмы: быстро, но приближённо. P_e = 1 - (сумма около 1), поэтому при очень малых P_e (около 10^-12 и     меньше) теряются значащие цифры. Например, P_e(36) во float = 7.92821e-09 вместо точного 7.92822e-09. Сравнение P_e <=  eps на границе тоже может ошибиться.

## Результаты (R = 2, eps = 10^-3, q = 5)

- P_e(n) <= eps впервые выполняется при n = 7: l = 6, P_e = 0.00084.
- При n = 8 ошибка снова большая: P_e = 0.166. Длина слова l округляется вниз и остаётся 6.
  Кодовых слов столько же, а блоков стало в 4 раза больше.
- Поэтому P_e(n) убывает не плавно, а скачками. Минимальное n - это ещё не n0:
  после него P_e может снова стать больше eps.
- R > H, поэтому n0 существует: при больших n P_e(n) -> 0.

R = 1.6 < H: с ростом n P_e растёт (0.62 при n = 10), n0 не существует.
Но при eps = 0.5 подходит n = 1. Это пример "малых n" из условия:
при малых n условие может выполняться, даже если R < H.

## Файл кода

n, l, q, алфавит и список взятых типов. Блоки идут по типам в порядке списка,
внутри типа - в лексикографическом порядке. Кодовое слово блока - его номер по основанию q.
Все q^l блоков не перечисляются: при больших n их слишком много.

# Задача 1.3. Архиватор ZipMeHuffman

## Запуск

./run.sh 1.3 compress файл [--stats]        # результат: файл.zmh

./run.sh 1.3 decompress файл.zmh          # результат: файл без .zmh

## Формат zmh

| Поле | Размер |
|---|---|
| сигнатура "ZMH1" | 4 байта |
| размер исходного файла | 8 байт |
| CRC32 исходного файла | 4 байта |
| размер сжатых данных | 8 байт |
| число разных байтов m | 2 байта |
| пары (байт, длина кода) | 2 * m байт |
| CRC32 заголовка | 4 байта |
| сжатые данные | остаток файла |

Размер заголовка: 30 + 2m байт.

Послкдний неполный байт дополняется нулями. Сколько символов декодировать,
известно из размера исходного файла, поэтому лишние нули не мешают.

Пустой файл: m = 0, данных нет, остаётся только заголовок 30 байт.
Файл из одного байта: единственному символу даётся код длины 1.

## Хранение модели

Храню только длины кодов, а не сами коды и не частоты. Код канонический:
по длинам декодер однозначно восстанавливает те же коды.

Другие варианты:
- частоты байтов: 4-8 байт на символ, больше;
- таблица из 256 длин: всегда 256 байт. Она получается короч пар, только если в файле больше 128 разных байтов.

В английском тексте 78 разных байтов: пары занимают 156 байт.
В русском 129: пары 258 байт, таблица была бы на 2 байта короче. Разница мала, а пары проще было сделать.


## Обнаружение повреждений

Проверки идут по порядку:
1. первые 4 байта не "ZMH1" - не тот формат;
2. файл короче заголовка - значит обрезан;
3. не сходится CRC заголовка - тогда повреждён;
4. данных меньше, чем записано в заголовке, то обрезан, если больше - повреждён;
5. не сходится CRC восстановленных данных - повреждён.

CRC32 находит любую ошибку в одном бите и любую пачку ошибок длиной до 32 бит.
Другие варианты: простая сумма байтов (не замечает перестановки байтов),
отсутствие проверки (ошибка часто не видна при декодировании).

Отдельный CRC заголовка нужен, чтобы ошибку в поле размера
не принять за обрезанный файл.

Инверсия одного бита в середине данных: декодируются другие символы,
CRC данных не сходится, программа пишет "файл повреждён".

Коэффициент = исходный размер / сжатый размер.

### Почему l больше H

Длина кода Хаффмана - целое число бит, а -log2 p обычно не целое.
Поэтому H <= l < H + 1. Для текстов разница около 0.04 бита.
Больше всего она у repeat.bin: H = 0, но при этом код не может быть короче 1 бита.

### Почему файл растёт

- cat.jpg: JPEG уже сжат и байты почти равновероятны (H = 7.97).
  Экономия на данных 203 байта, а заголовок 542 байта. Итог: файл больше на 339 байт.
- empty.bin: данных нет, получается остаётся только заголовок на 30 байт.

Сжатие уходит в минус, когда экономия на данных N * (8 - l) / 8 байт
меньше заголовка 30 + 2m байт.

### Русский и английский текст

У русского текста H на байт меньше. Насколько я понял, в UTF-8 русская буква занимает 2 байта,
и первый байт почти всегда 0xD0 или 0xD1. Он хорошо предсказуем, получается, что средняя энтрапия на байт меньше.
